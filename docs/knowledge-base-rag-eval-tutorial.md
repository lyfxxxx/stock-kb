# 从零理解财报知识库与 RAG 评测

> 面向没有知识库或大模型背景的读者。目标不是讲代码细节，而是讲清楚：知识库是什么、为什么需要它，以及当前评测方案为什么要这样设计。

## 1. 先理解一个核心问题：文件很多，但“查不到”

NAS 里可能有很多 PDF：年报、中报、研报、招股书。它们可以直接打开看，但很难自动回答这些问题：

- “海底捞 2024 年营业收入是多少？”
- “海底捞的现金流质量怎么样？”
- “哪些研报讲过百胜中国的门店增长？”

普通做法是手动翻文件、搜索关键词、再自己整理。知识库的目标，是把这些不可查询的文件变成可以查询、可以引用、可以追溯的数据。

所以知识库至少要能回答：

- 某个公司有哪些报告；
- 某个数字在哪个文件的哪一页；
- 某段原文讲了什么；
- 让 AI 基于这些原文来写笔记，而不是凭记忆编数字。

## 2. 知识库里其实有三种“查找方式”

可以把知识库想象成一个图书馆。三种查找方式对应不同场景：

| 方式 | 类比 | 适合什么 | 不适合什么 |
|---|---|---|---|
| 结构化查询 | 查图书馆目录卡片 | “2024 年营业收入是多少” | 解释、趋势、观点 |
| 关键词检索 | `Ctrl+F` 全文搜索 | “翻台率”“资本开支” | 意思相近但用词不同 |
| 语义/向量检索 | 问熟悉馆藏的管理员 | “现金流质量怎么样” | 必须精确到某个固定词 |

### 2.1 结构化数据

三大报表里的数字，比如收入、利润、总资产、经营现金流，最好解析成结构化表格：

```text
公司 | 报表类型 | 年份 | 科目 | 数值 | 来源文件 | 页码
```

这类问题不应该让 AI“猜”，而应该直接查数据库。比如：

> 海底捞 2024 年营业收入是多少？

系统应该从结构化表里查到一个确定的数字，并且知道它在哪一页。

### 2.2 关键词检索

关键词检索适合术语明确的问题，比如“翻台率”“同店销售”。它速度快、结果可解释，但缺点是：

- 中文需要特殊分词；
- 近义词、同义表达可能搜不到；
- 中英文混排时，“同店销售”和 “same-store sales” 可能没法互相命中。

### 2.3 语义/向量检索

语义检索不要求原文出现完全相同的词。它把文本变成一组数字，也就是向量。意思相近的文本，向量距离也近。

例如问“现金流质量怎么样”，原文可能写的是“经营现金流是否覆盖资本开支”，但语义检索仍然可能找到它。

向量检索的代价是：

- 结果不一定包含你输入的关键词；
- 排序不如关键词检索直观；
- 需要先生成向量，模型越大通常越慢、越占内存。

### 2.4 混合检索

实际系统通常把“关键词检索”和“向量检索”合起来：

```text
用户问题
   ├─ 关键词检索 → FTS5
   ├─ 向量检索   → embedding
   └─ 合并排序   → 最终 top_k
```

关键词负责“精确命中”，向量负责“语义补充”。当前 stock-kb 就是这种混合检索。

## 3. RAG 是什么

RAG 是 Retrieval-Augmented Generation，意思是：

1. 先检索相关资料；
2. 再让大模型阅读这些资料；
3. 最后生成回答，并且要求回答引用资料。

它解决的是大模型“幻觉”问题。大模型本身可能编数字；但如果我们先给它找到原文，并要求它只依据原文回答，错误概率就会降低。

所以 RAG 的核心不是“生成得多漂亮”，而是：

- 检索对不对；
- 引用的原文支不支持结论；
- 数字能不能追溯到文件和页码。

## 4. 当前项目的知识库流水线

stock-kb 的简化流程是：

```text
PDF / XLS / HTML
  → 解析文本和三大报表
  → 规范化（繁体转简体、行项目归一化）
  → 写入 SQLite
  → 建立 FTS5 关键词索引
  → 切块并生成向量索引
  → MCP 只读接口
  → AI 查询并生成笔记
```

当前规模大约是：

- 2 家公司：海底捞、百胜中国；
- 60 份报告；
- 8,128 页；
- 8,718 条三表行项目；
- 133 条财务指标。

## 5. 为什么评测系统容易“分数虚高”

一开始，评测很容易写成这样：

```text
如果三表里有这个科目，就算命中；
如果检索结果里包含查询词，就算命中；
如果前 5 条里有期望文件，就算命中。
```

这些规则单独看都有用，但混在一起会掩盖真实问题。

比如一道题：

> 海底捞 2024 年营业收入是多少？

旧逻辑只要三表里查到了“营业收入”，就记成 `rank=1`，即使检索结果第一条根本不是 2024 年报。于是报告里看起来 Hit@1=100%，但 AI 真正读的原文可能是错误年份。

所以优化后的评测设计有一个关键原则：

> 不同能力要分开打分，不能用一个“命中”代表所有能力。

## 6. 当前评测方案：三层分离

当前 `stock_kb/eval_runner.py` 把评测拆成三层：

### 第一层：检索质量，retrieval

只回答一个问题：

> 检索系统有没有把正确的原文页放到前面？

它只根据真实 `top_hits` 和人工标注的期望来源来判断，不允许三表命中来“帮忙”。

### 第二层：结构化质量，structured

只回答：

> 三大报表查询是否找到了正确的科目、数值和来源页？

这部分由 `statement` 触发，独立计算。

### 第三层：生成质量，generation

只回答：

> 最终笔记是否准确、完整、可溯源、无幻觉？

目前这一层还没有自动评分，需要人工或 LLM judge 完成。

这样设计后，就能区分三种失败：

- “三表查对了，但检索没找到原文”；
- “检索找到了原文，但三表值错了”；
- “三表和检索都对，但 AI 生成笔记时编了数字”。

## 7. 评测题型设计

当前题库在 `eval/questions.yaml`，共有 80 道题，分五类：

| 题型 | 验证什么 | 例子 |
|---|---|---|
| exact | 结构化精确数字 | 海底捞 2024 年营业收入 |
| keyword | 关键词检索 | 翻台率、资本开支 |
| semantic | 语义检索 | 海底捞的现金流质量怎么样 |
| cross | 中英跨语言检索 | Yum China same-store sales trend |
| end2end | 完整生成链路 | 写一篇海底捞笔记需要哪些材料 |

### 为什么 exact 不混入检索分数？

因为“营业收入是多少”最可靠的方式是直接查三大报表，而不是靠页面检索猜。把 exact 放进检索分数，会让检索指标虚高，也会让真正的语义检索问题看不清。

### 为什么题目要带“负样本”？

如果一道题只写“正确页”，系统只要返回任意相关页就可能得分，无法发现它是不是把错误年份、错误公司也排上来了。

负样本用于区分：

- “包含这个词，但其实是错误年份”；
- “包含这个词，但其实是另一家公司”；
- “看起来相关，但没有直接回答问题”。

## 8. 常用检索指标，用大白话解释

假设一道题有 5 条检索结果，正确答案出现在第 2 条。

### Recall@5

> 正确答案有没有出现在前 5 条里？

如果出现了，Recall@5 = 1；没出现，就是 0。它看的是“找得到吗”。

### Hit@1

> 正确答案有没有排在第 1 条？

这更严格，看的是“用户第一眼能不能看到”。

### MRR

MRR 是 Mean Reciprocal Rank，也就是“正确答案排名的倒数的平均值”。

如果正确答案排第 1，贡献 1/1 = 1；排第 2，贡献 1/2 = 0.5；排第 5，贡献 1/5 = 0.2。

它比“找得到吗”更能反映排序质量。

### nDCG

nDCG 更细致。它允许你给不同来源标不同相关度：

- 3 = 非常相关；
- 2 = 相关；
- 1 = 部分相关；
- 0 = 不相关。

然后看系统把高相关度的页面排得靠不靠前。这比“只有对和错”更适合语义题，因为语义题往往有多个相关页。

## 9. 用一个小例子理解打分

题目：

> 海底捞的现金流质量怎么样？

期望来源：

- A 文件第 41 页，相关度 3，required；
- A 文件第 40 页，相关度 2；
- B 文件第 5 页，相关度 1。

系统返回前 5 条：

```text
1. C 文件第 3 页   ← 不相关
2. A 文件第 40 页  ← 相关度 2
3. A 文件第 41 页  ← 相关度 3
4. B 文件第 5 页   ← 相关度 1
5. D 文件第 10 页  ← 不相关
```

这时：

- Recall@5 = 1，因为 required 的第 41 页在前 5 条里；
- Hit@1 = 0，因为第 1 条不是正确答案；
- MRR = 1/3，因为第一个命中的 required 来源在第 3 位；
- nDCG 会根据 0、2、3、1、0 的位置计算，比 Recall 更能反映排序好不好。

## 10. 当前新评测结果怎么看

当前检索层结果，只统计真正的检索题：

| 方案 | keyword Recall@5 | semantic Recall@5 | cross Recall@5 |
|---|---:|---:|---:|
| FTS5 | 0.750 | 0.000 | 0.167 |
| bge-small-zh + FTS | 0.550 | 0.300 | 0.167 |
| BGE-M3 + FTS | 0.550 | 0.250 | 0.167 |

这些数字告诉我们：

- FTS 擅长关键词，不擅长语义；
- 向量检索能补上部分语义能力；
- 跨语言检索仍然是最明显的短板；
- 模型更大不代表一定更好，BGE-M3 在这个小语料上并没有超过 bge-small-zh。

结构化层 26 道带 `statement` 的题全部命中，说明三大报表直查是可靠的。但需要注意，当前数值是从数据库读取的 v1 golden，还需要人工从 PDF 独立复核，才能证明“解析值真的和原文一致”。

## 11. 你可以怎么动手学习

如果第一次接触这个项目，建议按下面顺序走一遍：

```powershell
python -m stock_kb stats --json

python -m stock_kb search "翻台率" --top-k 5 --json

python -m stock_kb search "现金流质量" --hybrid --json

python -m stock_kb eval

python -m stock_kb eval --model BAAI/bge-small-zh-v1.5
```

然后打开这几个文件对照：

- `eval/questions.yaml`：看题目、答案来源、负样本怎么标；
- `stock_kb/eval_runner.py`：看评分怎么算；
- `PLAN.md` 第 16 节：看这次优化记录和当前基线。

1. 结构化查询、关键词检索、向量检索分别解决什么问题？
2. 为什么财务知识库不能只靠向量检索？
3. RAG 中的“检索”为什么必须和“生成”分开评测？
4. Recall@5 和 Hit@1 的区别是什么？
5. 为什么 exact 题不应该用检索排名来判分？

7. 当前系统真正的短板是哪里？

如果能回答大部分，你已经理解了当前知识库和评测系统的核心设计。下一步再深入，就是读代码、做实验，或者为语义和跨语言检索设计更好的检索策略。
